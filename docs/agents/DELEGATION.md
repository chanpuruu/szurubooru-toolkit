# Delegation

Read before delegating. Routine local exploration, edits, and focused checks should normally be done directly.

Use delegation only when permitted by the active instructions and useful for independent workstreams, a bounded specialist review, or a substantial read-only investigation. Do not delegate to avoid understanding the controlling code.

Every dispatch needs one objective, exact paths, known facts, exclusions, edit permission, acceptance criteria, verification, stop conditions, and a concise reporting format. Keep mutable file ownership disjoint. Do not parallelize unresolved interfaces, shared fixtures, migrations, lockfiles, or the same configuration.

For future web work, agree the API/event/job contracts before distributing frontend and backend tasks. Scaffolding, job execution, security, and all command workflows are separate acceptance boundaries even when they ship in one release.

Treat returned claims as evidence, not proof. Verify against actual code and focused checks; resolve contradictions before relying on them. In particular, distinguish internal CLI threads from queue workers, and planned services from existing dependencies. The parent owns the final diff, tests, and report.
